# 协议消息覆盖清单

## 1. 统计口径

本清单以 `jt-protocol` 中带 `@Message` 的协议消息类为主口径，审计日期为 2026-08-10。
“73 类”是 Java 消息类数量；部分类复用多个消息 ID，因此展开后共有 85 个 ID。当前入口与统一投递目标必须分开理解：

- **上行 endpoint**：当前 `jt-signal` 中存在对应 `@Mapping`，表示已有终端上报业务处理入口。
- **下行 controller**：上游 REST 路由 `/device/{ID}` 已迁入当前 `jt-signal`，共保留 52 个 POST 处理入口（JT/T 808 为 37 个，JT/T 1078 为 15 个）。
- **自动应答**：由注册、通用应答、分包补传或文件处理流程生成，不要求独立 REST 路由。
- **统一 adapter**：所有成功解码且已完整重组的入站消息都会在 endpoint/controller 分派前进入投递通道；当前实现已通过 73 类消息动态扫描与投递验收。

汇总如下：

| 协议族 | 消息类 | 展开 ID | 当前 endpoint 覆盖 ID | 上游 controller 覆盖 ID | 自动应答 ID | 无专用入口 ID |
|---|---:|---:|---:|---:|---:|---:|
| JT/T 808 | 54 | 61 | 25 | 31 | 5 | 0 |
| JT/T 1078 | 14 | 18 | 4 | 13 | 0 | 1 |
| T/JSATL12 | 5 | 6 | 4 | 1 | 1 | 0 |
| **合计** | **73** | **85** | **33** | **45** | **6** | **1** |

类级统计中，31 类至少有一个当前 endpoint，42 类没有当前 endpoint。三个复用类只覆盖了部分方向：`T0001`、`T8003`、`T0A00_8A00`。

此外还有 11 个由基础 `JTMessage` 或命令参数承载、但没有专用 `@Message` 类的通用入口，因此不计入 73 类/85 ID：

- endpoint：`0x0002`、`0x0003`、`0x0004`、`0x0701`。
- 上游 controller：`0x8104`、`0x8107`、`0x8201`、`0x8204`、`0x8700`、`0x8702`、`0x9003`。

现有 endpoint 共 36 个 `@Mapping`、覆盖 37 个 ID，其中 33 个属于下表；上游 controller 共 52 个 POST 路由，其中 45 个属于下表。

## 3. 统一投递入口设计

### 3.1 注入点与顺序

统一入口应放在 `JTMessageAdapter.decode(ByteBuf, Session)` 完成解码之后，由
`decodeLog(Session, JTMessage, ByteBuf)`（或同等的专用回调）调用投递 adapter。不要只依赖
`HandlerInterceptor.beforeHandle`：没有 handler 的消息会直接进入 `notSupported`，可能绕过该回调，
`T9105` 和未知消息就会再次遗漏。

投递准入必须发生在 endpoint 分派以及 `@Async`/`@AsyncBatch` 之前，以设备标识作为顺序键，保持同一设备的到达顺序。`MessagePublisher.publish` 是有界、非阻塞的准入接口，不表示消息已经送达；调用方必须检查返回值。关键消息在内存队列溢出时由 `jt-delivery` 持久化到磁盘并保留顺序；只有磁盘保留也失败时才返回 `RETRY_REQUIRED`，此时 `jt-signal` 明确记录高优先级错误，不再叠加第二层重试队列。

### 3.2 完整分包后才投递

当前 `JTMessageDecoder` 在分包尚未收齐、`addAndGet` 返回 `null` 时仍会返回只有头部的消息对象。
统一 adapter 必须阻止该对象进入投递通道，避免每个残包被当作完整业务消息重复投递。验收条件如下：

1. 原子包在完整解码后投递一次。
2. 分包报文只在全部分包重组并完成消息体解析后投递一次。
3. 超时残包只触发补传/丢弃与日志，不产生业务信封。

可在 decoder 未完成时返回 `null`，或设置明确的“重组完成”标志供 adapter 判断；不得用消息体字段是否为空进行猜测。

### 3.3 未知消息

未知 ID 没有 body schema 时，decoder 应返回基础 `JTMessage`，保留消息头信息。adapter 先记录并按 `unknown` 语义投递可用元数据，随后框架走 `JTHandlerInterceptor.notSupported` 返回平台通用“不支持”应答。整个过程不得抛出未处理异常或断开终端连接。

### 3.4 二进制负载过滤

信封 payload 只允许展开后的 JSON 兼容业务字段，禁止放入 `ByteBuf`、`byte[]`、`ByteBuffer` 或文件内容。涉及二进制字段的消息类至少包括：

`DataPacket`、`T9208`、`T0608`、`T0700`、`T0705`、`T0801`、`T0901`、`T0A00_8A00`、`T8108`、`T8701`。

文件类消息必须先完成重组与落盘，再投递文件标识、类型、大小、关联报警信息和访问地址。`DataPacket` 的消息 ID 是 `0x30316364`，超过 16 位；信封的 `messageId` 必须保持无符号 32 位范围 `0..0xffffffff`（当前模型已按此范围校验），不得回退为 16 位约束。

## 4. 验收结论

- 73 个消息类与 85 个类内 ID 已逐项列出，协议族计数为 JT/T 808 `54/61`、JT/T 1078 `14/18`、T/JSATL12 `5/6`（类/ID）。
- 85 个 ID 中，33 个有当前 endpoint、45 个有上游 controller、6 个由流程自动应答，唯一没有专用入口的是 `T9105/0x9105`。
- `T9105` 必须由统一 adapter 补齐投递；其后仍可因无业务 handler 返回通用“不支持”应答，但不得丢消息或断链。
- 已通过自动化验收：动态扫描确认恰好 73 个 `@Message` 类且每类均进入投递；完整分包仅投递一次；未知消息返回“不支持”且不断链；文件二进制不进入信封；`DataPacket` 的无符号 32 位消息 ID 保持完整。`mvn -B -ntp -pl jt-signal -am test` 与 `mvn -B -ntp -pl jt-boot-all -am test` 均已通过，standalone 实际监听 `7100/TCP`、`7101/UDP`，cluster 实例 1 实际监听 `7111/TCP`、`7112/UDP`。
